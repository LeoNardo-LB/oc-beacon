# DSH 0.1.5-rc.1 升级影响调研（oc-beacon 客户端适配）

> 状态：**调研完成**（2026-09-10）。方法 = 官方发布说明 + 双 tag 源码 diff + 在役 0.1.5-rc.1 实例只读活体探针，三源交叉验证。
> 一句话结论：**传输/API 接口面（RPC 方法、信封、mux 流、鉴权）向后兼容，只增不减；真正的破坏性变更在"会话数据格式 V3"，它改变的是会话事件词汇与实时流式通道——当前 APK 连 0.1.5 宿主会出现"历史整页拒绝重建（空白）+ 无实时 token 流"。修复面集中在 oc-beacon 的 DSH 适配层 4 个文件，不动上层架构。**
> 关联：backlog #269（DSH 原生接入）、#317/#318/#319（0.1.2 适配）、#378（转录实体/表面遮蔽）、#349（subagent 卡）、#385（注入卡）。
> 基线文档：`docs/specs/2026-08-31-dsh-integration-design.md`、`docs/journal/2026-09-04-dsh-012-adaptation.md`。

## 2. 变更总览（按发布说明分类）

**新增功能（客户端可感知）**：DeepSeek-V41-Flash（`deepseek-flash`）适配器（文本/图片/会话内系统提示词更新）并成为新会话默认模型；Web 任意类型文件上传；可继续对话子代理的排队/编辑/删除/Steer/停止；动态系统提示词且不破坏 KV Cache（模型需显式声明）；Web 右侧 Sidebar 多标签/分栏/全屏与多格式预览（原 Detail 面板移除）；模型探测支持自定义 provider `models` 与 Anthropic 原生列表；出站请求遵循 `HTTP_PROXY` 等；Web "在应用中打开"；`/feedback` 独立反馈。

**体验与修复**：目标暂停即终止当前轮次且仅用户可恢复；DeepSeek 流式工具调用续传分片不再用空值覆盖 call id/name；Web 断线自动恢复；发送/窗口调整后自动滚底；会话运行中发送与 Enter 行为一致；拒绝空消息/空白队列编辑；项目根目录权限/IO 错误显式上报；折叠思考摘要去掉 Markdown 粗体标记；Windows 盘符根 Workspace；模型目录失效不再隐藏设置入口；Base URL 校验；MCP 重复分页游标拒绝；等等。

**其他变更（开发者面）**：**会话数据格式 V3**；**Session 生命周期 `SessionHandle` + session 锁 + `agentLoop.create()` 异步**；默认工具调整（SDK/Headless/ACP 用 read/write/edit；Web minimal 与 sdk-minimal 默认仅持久 shell、`str_replace_editor` 需显式启用）；普通 subprocess handle 不再暴露 pid；`FS_NOT_OBSERVED` 诊断统一；Python SDK macOS x64 wheel；pi-ai 0.85.1；子代理插件运行时升 Codex 0.153.4 / Claude Code 2.1.263；自定义 persona 拆前缀/后缀；**插件 Agent API 移除 `ctx.agent`**；**Inbox API 改为类型接口**；**Web 插件面板 API 改为 `sidebar.panellist`/`main`**；Agent Teams 包可 npm 安装（需显式加 profile）。

## 3. 传输/API 线面差异：**兼容**

### 3.1 RPC 方法面：只增不减

对全仓（`packages` + `apps`）以 `@Remote` 装饰器提取方法签名并排序做差集：

- 0.1.2-rc.1：**182** 条；0.1.5-rc.1：**202** 条。
- **无删除、无改名**；差集全部是新增（另有若干描述文案变化与 `async` 关键字位置变化，非语义）。

新增方法（含命名空间归属）：

| 命名空间 | 新增方法 | 用途 |
|---|---|---|
| `workspace-files`（新包） | `list` / `read` / `readAll` / `readBytes` / `readRelated` / `stat` / `changes`(stream) | 工作区文件读取、字节窗口、stat、变更流 |
| `fileUploads`（新包） | `upload` | 编码上传落盘并投递给 Agent |
| feedback 域（新包 `command-feedback`） | `record` | `/feedback` 独立反馈 |
| `goal` | `get` | 读取精确 live agent 的当前目标 |

> 证据：`packages/api/workspace-files/src/index.ts`、`packages/client/file-upload/src/index.ts`、`packages/feedback/command-feedback/src/index.ts`、`packages/goal/goal/src/index.ts`（均仅在 0.1.5 tag）。

oc-beacon 依赖的既有方法（`session/list|create|rename|fork|cancel|prompt|page|selectModel|modelCatalog`、`subagents/*`、`goals/*`、`commands/*`、`agentPresets/*`、`llm/*`、`settings/*`、`credentials/*`、`directoryPicker/*`、`skills/list`、`pluginInventory/list`、`messageFeedback/*`、`fileReferences/list`、`sessionReferenceResolver/candidates`）**全部保留**。

### 3.2 信封 / mux / 鉴权 / 错误码：不变

- `packages/api/gateway/src/stream-protocol.ts` 两 tag **blob hash 完全相同**（`142598863ec569193504373b5c6137e76e84b6fa`）——`/api/remote.mux`、`$events/result`、`open/cancel/item/error/end` 帧词汇、"$events 逻辑流" 语义均未变。
- `packages/api/gateway/src/index.ts` 的唯一改动是内部 `identifyHost`→`source.context.agentId`（插件/宿主内部身份解析），**不影响线面方法名与帧**。
- 鉴权：`packages/client/connection/src/browser-auth.ts` 与 `packages/credentials/authorization/src/**` 未改；token→303+Set-Cookie、cookie 绑 authority、RPC/WS 挂 Cookie 的机制不变。`packages/client/connection/src/index.ts` 改动 32/20 行，属恢复/上传接线，不涉鉴权协议。
- 错误码：0.1.2 的 39 值闭集定义位于**生成的声明文件 `rpc.d.ts`**，仓库源码中检索不到字面量，本次未逐码 diff；发布说明未列出错误码变更，且 oc-beacon 对闭集外错误码本就保留原串容错（`DshRpcErrorCode.isKnown=false` → `Unknown` 兜底），**风险低**。

### 3.3 载荷级附加变化（向后兼容）

- `session/prompt` 的 `PromptContentPart` 新增 `{ type: 'file', receiptId }`（先 `fileUploads/upload` 得到 receipt）；文本/图片旧 part 不变（`packages/api/session-controller/src/types.ts`）。
- `session/openWorkspacePath` 新增可选 `action?: 'reveal'`；新增 `workspaceDesktop()`（宿主桌面描述）。
- `session/follow` 新增可选 `assistantStream?: true`（另见 §4.3）。
- `rpc.ts` 的 Fetch route 新增 `POST` 与 `requestBody: 'buffered'|'streaming'` 模式（为通用文件上传服务），旧 GET/HEAD 路由不受影响。
- gateway `TypertRemoteEventContext` 增 `agentId` 字段（宿主内部 waterfall 投递），线面 waterfall 帧结构不变。

## 4. 会话数据格式 V3：核心破坏性变更

服务端把会话数据格式从 V2 升级到 V3。官方迁移文档：`packages/session/session-format-v2-to-v3/README.md`（`.../README.zh.md`）。**旧日志由版本迁移生成新文件并保留原文件；升级后的会话不支持降级读取。** 这意味着客户端在 0.1.5 宿主上读到的**所有**会话都是 V3 形状。

### 4.1 事件词汇增删（authoritative：`packages/core/session/src/known-event-types.ts`）

| 操作 | 事件 |
|---|---|
| **移除** | `assistant/chunk`、`tool/code-dispatch`、`tool/code-dispatch-start` |
| **新增** | `assistant/attempt`、`system/message`、`tool/ptc-dispatch`、`tool/ptc-dispatch-start`、`feedback/message-put`、`feedback/message-delete`、`subagent/catalog`、`deliverables/presented` |

### 4.2 载荷与信封形状（`packages/core/session/src/types.ts` + `packages/api/session-controller/src/types.ts`）

- `assistant/message` 增 `stream: AssistantStreamRecord[]`——**精确带时间的模型流被内嵌进整装消息**（chunk 不再独立成事件）。
- 新增 `assistant/attempt: { turn, step, stream }`——失败/重试/取消/stream-error 且未产生表面消息的 attempt。
- 新增 `system/message: { turn, step, message: SystemMessage }`——系统提示词成为**表面节点**；迁移保证"首个 `step/start` 后立即插一个 `system/message`（即使为空）"，即**每个 V3 会话至少有一个 `system/message`**；`request/header.data.header.system` 被移除。
- **表面替换指令改名**：`SessionWireSurfaceOp` 的 replace 由 `{op:'replace', start, end}` → `{op:'replace', startSeq, endSeq}`；`sourceEventSeqs`/`surfaceOp` 类型放宽为 `JsonValue`（opaque）。注意：`compaction/summary|prune.data.shadowedRange` 的 `start/end` **保持不变**（迁移只重映射其数值），改名仅限**信封级 surfaceOp**。
- **follow 快照 header 改字段**：`seedLength?: number` → `isSeeded: boolean`，并携带 `version: 3`（活体实测）。
- **`session/page` 记录类型收窄**：`SessionHistoryRecord = SessionEventEntry`；旧的 `{type:'chunks', event: chunkrow/*}` 打包记录**整体移除**（`history.ts` 删除了 `packChunkRuns/chunkEntryFor/pageRecords` 的打包逻辑，改为纯 `entryFor`）。
- `system/message`/`user/message`/`assistant/message`/`tool/result` 四类表面事件要求 `surfaceOp`；assistant 表面消息禁止 `sourceEventSeqs`。

### 4.3 实时流式通道迁移（对移动端最致命）

- `assistant/chunk` 在 0.1.5 中**只出现在 v0→v1 / v1→v2 迁移代码**里，不再是当前事件模型的可持久事件。
- 实时 token 改由 `session/follow` 的 **opt-in** 参数驱动：请求带 `assistantStream: true` 时，快照附 `assistantStream` baseline，增量帧为 `{ type:'assistant-stream', frame }`；frame 三态：
  - `start: { attemptId, revision, startedAfterSeq, turn, step }`
  - `chunk: { attemptId, revision, index, time, chunk: StreamChunk }`
  - `end: { attemptId, revision, index, outcome: {kind:'committed',eventType,seq} | {kind:'abandoned'} }`
  另有 client-only `assistant/live-chunk` / `transient` 记录型。
- 官方 Web 客户端在 `packages/api/session-controller/src/client/transport.ts:181` 显式 `assistantStream: true`。
- **不带该参数就收不到任何增量 token**；只会收到轮次结束后的整装 `assistant/message`。

## 5. 会话生命周期与其他服务端变更（对 Android 客户端无直接影响）

以下属宿主/插件内部 API，oc-beacon 是**外部线面客户端**、不加载 DSH 插件、无 JS 运行时，故不直接受影响；**若部署侧有自研 DSH 插件则需迁移**：

- **Session 生命周期**：persistence API 改为生命周期持有的 `SessionHandle`；`agentLoop.create()` 改异步；新增 session 锁（同一 session 至多被一个进程持有）。
- **插件 Agent API**：移除 `ctx.agent`，调用方显式传 Agent；可继续对话子代理归属修正（不被当根会话参与定时调度）。
- **Inbox API**：`Inbox` 改为类型接口，不再导出可构造运行时类；插件经 `agent.inbox` 读写；`hasPending`/`claim` 移出公共接口。
- **Web 插件面板 API**：改用 `sidebar.panellist`/`main`；原 `conversation` Slot → `main.conversation`。
- **persona 配置**拆前缀/后缀；**默认工具**调整（见 §2）；subprocess handle 不再暴露 pid；pi-ai 0.85.1；Codex/Claude Code 运行时升级。
- 模型：`DeepSeek-V41-Flash` 默认且支持图片输入——oc-beacon 若据模型 input 能力位门控图片附件，可自然受益（附加能力，不破坏）。

## 6. 活体实证（在役 0.1.5-rc.1 @ 3080）

**只读 RPC 扫描**（`session/page` 分页回溯到会话头部，7 个非空白会话，共 32,748 条记录）：

- 记录类型：`event` × 32,748；**`chunks` × 0**（与 §4.2 一致）。
- 事件类型实见：`tool/ptc-dispatch` 5,924、`tool/ptc-dispatch-start` 5,925、`assistant/attempt` 185、`system/message` 8、`deliverables/presented` 3、`assistant/message` 3,887、`tool/call|result` 各 3.7k、`compaction/*` 30、`command/run|done` 各 10 等。
- **`assistant/chunk` = 0，`tool/code-dispatch*` = 0**（确认旧词汇归零）。
- `surfaceOp` 键形状：`('endSeq','op','startSeq')` × 15——确认信封级替换已改名。

**WS `session/follow` 快照**（cookie 升级 101）：

- header = `{"version":3, "id":..., "createdAt":..., "cwd":..., "isSeeded":false, "agentPreset":"standard"}`——**version:3、isSeeded、无 seedLength**。
- records = 303，**firstRecordTypes 全为 `event`**，无 `chunks`。
- 带 `assistantStream:true` 时快照多出 `assistantStream` baseline；不带则无该键。
- 12s 观察窗内目标会话无活跃 token 输出，故未捕获 `assistant-stream` 增量帧（机制存在性由源码 + baseline 证实）。

## 7. 对 oc-beacon 的影响分级

### P0 — 阻断，必须修（当前 APK 对 0.1.5 宿主不可用）

1. **历史整页拒绝重建 → 空白转录。** oc-beacon 映射器对未知且无 `ignorable` 的事件落 `UNKNOWN_UNIGNORABLE`（`DshEventMapper.kt:853-859`）；`DshHistoryFolder` 收集后置 `refusedRebuild`（`DshHistoryFolder.kt:69`、:119）；`DshApiClient.readMessages` 随即返回空 `MessagePage`（`DshApiClient.kt:1097-1101`）。V3 的 `system/message`/`assistant/attempt`/`tool/ptc-dispatch*`/`deliverables/presented` 等**都不在当前词汇表**，而活体证明它们在真实会话中大量存在——**几乎每个会话都会命中拒绝**。
2. **子代理卡消失（#349）。** `tool/code-dispatch(-start)` 分支（`DshEventMapper.kt:821-822`、`mapCodeDispatch*`）在 V3 永不命中；V3 是 `tool/ptc-dispatch*`。
3. **实时流式消失。** 实况映射挂在 `"assistant/chunk" -> mapChunk`（`DshEventMapper.kt:599`），V3 不再产生该事件；新的 `assistant-stream` 帧既未 opt-in 也未映射。
4. **压缩/遮蔽折叠失效（#378）。** `surfaceOp` 读 `start/end`（`DshEventMapper.kt:909-922`）→ V3 为 `startSeq/endSeq` → 读空并打点"残缺"，折叠指令被丢弃（`shadowedRange` 路径不受影响，`start/end` 保持）。

### P1 — 功能/渲染降级（P0 修好后才暴露）

- `system/message`：即使不拒绝，也需决定呈现策略（系统提示词/注入卡；DSH Web 将其作为会话内系统节点）。当前无处理。
- `assistant/attempt`：失败/重试/取消尝试的可视化（当前无）。
- `deliverables/presented`：产物交付卡（新增能力）。
- `subagent/catalog`、`feedback/message-put|delete`：新事件，需至少容错/建模。
- `session/page` 的 `chunks` 过滤与 `DshHistoryFolder` 的 `assistant/chunk`/`seq0` 跳过在 V3 成死代码（无害），可清理。

### P2 — 新能力机会（非必须）

- **文件内容查看**：`workspace-files` 的 `read/readAll/readBytes/stat/changes` 可开启当前被能力位关闭的"文件查看/搜索"（设计文档 §2.6 曾因"无读取方法"置 false）。
- **任意文件上传**：`fileUploads/upload` + `session/prompt` 的 `{type:'file',receiptId}`。
- **独立反馈**：`/feedback` + feedback `record`。
- **目标读取**：`goal/get`。
- **模型图片能力**：DeepSeek-V41-Flash 默认模型支持图片。

### 无影响

RPC 方法名/payload（既有）、鉴权与 Host 栅栏、mux 信封与 `$events/result`、`session/page` 请求参数、`session/list` 条目字段、`session/subscribed` 基线（oc-beacon 由 `lastSeq` 合成，不消费 header，故 `seedLength→isSeeded` 无影响——已 grep 确认）。

## 8. 逐文件修改清单与建议方案

> 全部落在 DSH 适配层；上层（EventDispatcher/FSM/UI）零改动，延续 journal 2026-09-04 "合成 0.1.1 帧词汇隔离版本差异" 的既有策略。

1. **`app/src/main/kotlin/.../data/api/dsh/DshEventMapper.kt`（主战场）**
   - 事件词汇表补全（保留旧词以兼容 V011/V012 宿主）：
     - 新增映射：`tool/ptc-dispatch`→`mapCodeDispatch`、`tool/ptc-dispatch-start`→`mapCodeDispatchStart`（复用 #349 子代理卡）；
     - `system/message`：作为系统/注入卡呈现（可复用 `mapUserMessage` 的 `injectionKind` 路径或新增 `Message.System`），至少不得落 UNKNOWN；
     - `assistant/attempt`：可选渲染"失败尝试"（至少 `Ignored(LOG_ONLY)` 或新 reason）；

## 9. 版本/能力探测建议

- 0.1.5 与 0.1.2 的 RPC/mux 线面**完全相同**，现有"slash+args vs dot+裸"双形态探测仍判 `V012`，**无法区分 V012/V015**。
- 建议能力探测（择一或组合）：
  1. `session/follow` 快照 header `version`（V3=3；注意 header 可能不总是携带）；
  2. 事件词汇出现 `system/message` / `tool/ptc-dispatch`；
  3. 方法存在性：`session/page` 之外探测 `workspace-files/list`、`fileUploads/upload` 等新方法（404 判旧）；
  4. `session/list` 的 `projections` key 集差异。
- `host.describe` 自 0.1.2 起无对应，不可用于版本锁定（且历史版本号曾硬编码为 `"0.0.1"`）。
- **pre-release 无兼容承诺**：建议客户端做**容错优先**（未知事件不拒绝重建，降级为忽略并打点），而非硬版本门禁——否则未来每次词汇扩展都会重演本次"整页空白"。

## 10. 风险与验证计划

**风险**
- V3 迁移**不可降级读**：宿主一旦升级，未适配的 APK 会让 DSH 会话历史全空；需尽快适配或给用户明示。
- 迁移保留原文件（文件层可回滚），但"升级后的会话不支持降级读取"是语义红线。
- `assistant/attempt` 等新事件若继续按"未知→拒绝重建"处理，词汇每扩展一次就会复发；建议把"未知不可忽略→拒绝整页"改为"具名降级 + 可观测"，仅对 `surfaceOp` 等结构性破坏才拒绝。

**验证**
1. 单测：以活体抓取的 V3 会话页为黄金样本，断言 fold 不拒绝、事件计数、surfaceOp `startSeq/endSeq` 解析、`assistant-stream` 三态映射；补 `tool/ptc-dispatch`→子代理卡、`system/message` 渲染用例。
2. 容器回归：用 `dsh-keepalive-e2e:0.1.2*` 靶机验证 V012/V011 不回归（旧词汇仍走旧分支）。
3. 真机 E2E：对 3080（0.1.5-rc.1）走既有关卡（列表/历史/发送/流式/中断/重连），确认由"历史空白"转为正常渲染、且 token 增量可见。
4. 观测：logcat 中 `history fold refused rebuild` 归零、`surfaceOp.replace 残缺` 归零、`follow 未知值型/record 未知型` 有预期计数。

## 12. 附：适配层成色评估（架构视角，2026-09-10）

> 问题：现有架构能否很好隔离 DSH 版本变动（接口不稳定）？是否有一个独立适配层？是否足够优秀、足够动态？
> 结论：**有一层"传输 ACL"，但还不是"语义 ACL"；静态、编译期、事件面零版本维度，且以 fail-closed 应对未知。** 0.1.1→0.1.2 的整批吸收（上层零改动）证明传输层隔离有效；V3 击穿的正是未被隔离的数据语义面。

### 12.1 隔离边界确实存在（代码事实）

- 独立包 `data/api/dsh/`（18 文件 ≈7,900 行）；`DshApiClient` 实现 7 个域接口（SessionApi/MessageApi/SystemApi/FileApi/ProviderApi/TerminalApi/ShellApi）。
- 上层经 `*ApiImpl.pick(conn)` 的 `ServerType.Dsh -> dsh` 路由（7 处）；domain/UI 不写 DSH 特判，差异收敛为 `ServerCapabilities` 能力位（`ServerConnection.kt:121`）。
- RPC 唯一收口：`DshRpcClient.prepare()`（:224-225）→ `DshWireAdapter.method/payload`（命名 + args 包装）；`DshEnvelope` 四象限开放联合容错。
- 版本经接口 seam 注入：`DshProtocolSource`（生产 `DshProtocolSourceAdapter` → `DshConnectionRegistry`；测试 `DshUnprobedProtocolSource`）。
- mux 侧 `DshMuxSynthesizer` 把 0.1.2 帧合成 0.1.1 词汇（`DshRemoteMuxEngine.kt:51-54` 宣称 orchestrator/mapper/handler 零改动）。
- 30+ DSH 单测 + 4 个 fixture（`app/src/test/resources/dsh/`）。

### 12.2 但它只隔离了"传输/命名"，没隔离"数据/语义"

失败发生在数据面（V3 事件词汇），说明隔离边界画在了错的深度：

1. **版本是编译期二元枚举** `enum DshWireProtocol { V011, V012 }`，非能力描述符；新增一代要动 enum + 37 处 `protocolOf()` 调用 + 29 处字面分支（全在 `DshApiClient`）。
2. **语义构造散落在 god class 调用点**：`DshApiClient` 2,550 行、29 处版本分支，大量是语义差异（create 无 title、history→page、prompt requestId/mediaType、goals args、waterfall 回程 `$events/result`、providers groups 形态）；`DshWireAdapter` 只做机械翻译（设计文档 §2.3 自述"带语义变化的载荷由调用点构造，不经本类"）。**这是"枚举 + 调用点 if"，不是数据驱动适配器。**
3. **事件词汇零版本维度**：`DshEventMapper` 是无状态 `object` + 单个 `when(type)`；`DshHistoryFolder.fold()` 无 protocol 参数。V3 事件语法变更**完全绕过版本适配器**直达核心 fold——这正是本次击穿的机制。
4. **fail-closed 且页粒度**：未知且无 `ignorable` → `UNKNOWN_UNIGNORABLE` → 整页拒绝重建（刻意设计，被 `DshHistoryFolderTest` 锁定断言 `refusedRebuild=true`）。词汇演进 = 历史空白，而非降级渲染。
5. **无运行时能力探测/缓存**：`DshConnectionRegistry` 仅以 slash/dot 双探判定 V011/V012；`unsupported()` 是硬编码版本判据，不是"探测到方法不存在"；无方法存在性 / 事件词汇 / projections key 探测（设计文档 §5 曾提出，未落地为通用机制）。
6. **规范化模型是 0.1.1 最低公分母**：`DshMuxSynthesizer` 把新帧词汇压低到 0.1.1。对命名/传输差异极优，对真正新增的语义（`system/message`、`assistant-stream`、`assistant/attempt`）**无法表达**——LCD 防腐层的固有上限。
7. **架构文档未登记**：`docs/architecture.md` 无 DSH/适配层章节（grep 零命中）；ACL 只存在于代码。
8. **fixture 是单版本快照**：无 per-format-version 黄金样本矩阵；`DshWireAdapterTest` 是手写用例表而非数据驱动矩阵。

### 12.4 改进建议（可落地）

1. **版本枚举 → 能力/特性描述符**：连接时探测并缓存 `DshCapabilities`（wireGeneration、methodSurface 集合、eventVocabulary 版本、snapshot headerVersion），用特性判断替代 `protocolOf() != V012`；把 `ServerCapabilities` 从"serverType 单块"扩展为可表达 DSH 内部代际的能力位（如 `dshSessionFormatV3`、`dshAssistantStream`、`dshWorkspaceFiles`）。
2. **数据驱动适配表**：把 `DshWireAdapter` 从"命名/包装"扩为"每端点 × 每代 payload spec"（每代一个 `WireProfile`），消灭调用点 29 处 if。
3. **事件词汇版本化**：`DshEventMapper` 接受 `EventVocabulary`（V2/V3 映射）或用 `type → handler` 注册表按代装配；未知类型默认**具名降级 + 遥测**。
4. **fail-closed 分层**：页级拒绝只保留给"结构不可重建"（乱序、seed 缺失、surfaceOp 越界）；词汇未知 → 局部折叠卡 + Diagnostics 计数，保证主流程可用。
5. **契约/黄金样本矩阵**：每个 format version 一份 golden session log + 期望 `SseEvent` 快照；加"漂移检测"（对比服务器已知词汇集，未知即诊断）。
6. **架构文档登记 ACL**：`docs/architecture.md` 增 DSH 适配层章节与承重规则（版本差异只允许出现在适配层/词汇表）。
7. **拆分 god class**：按域拆 `DshSessionApi`/`DshFileApi`… 或按 wire profile 注入 payload builder。

### 12.5 一句话

现有适配层是一层不错的**传输 ACL**（0.1.1→0.1.2 整批吸收、上层零改动已证有效），但**不是语义 ACL**：它静态、编译期、事件面无版本维度，并以 fail-closed 应对未知。要"很好隔离"DSH 的不稳定，需要把版本升级为能力描述符、把 payload/事件适配数据驱动化、把未知的默认处置从"拒绝"改为"降级 + 遥测"。
