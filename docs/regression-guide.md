# 回归验证指南（Regression Verification Guide）

> 本文档指导**涉及已有能力的变更**（重构、接口调整、存储改造、性能优化、bug 修复等）如何执行系统性回归验证，确保既有功能不被破坏、新功能符合预期。变更分类、验证维度、能力域清单、问题处理流程一体化。

---

## 1. 定位与触发条件

### 1.1 文档定位

| 文档 | 角色 | 关系 |
|------|------|------|
| `docs/verification-requirements.md` | **验证总纲**——何时声称完成、4+1 维强制框架 | 上位文档，本文档遵守其铁律 |
| **本文档** | **回归执行指南**——变更后如何系统验证既有能力 | 总纲的实践细则 |
| `backlog.md` | 问题登记去向 | 非阻塞问题登记处 |
| `docs/chatscreen-editing-protocol.md` | ChatScreen 编辑协议 | 涉及 ChatScreen 时叠加遵守 |

**核心原则**：verification-requirements.md 回答"完成前必须做什么"；本文档回答"变更后既有能力如何系统验证"。

### 1.2 变更分类与回归级别

| 变更类型 | 例子 | 回归级别 |
|----------|------|----------|
| 接口/签名变更 | Repository 接口 suspend 化、参数/返回值变化（如 #38 DraftRepository） | **完整回归** |
| 状态机/数据流变更 | SessionStateService/FSM、SSE 事件处理、combine 源增删（如 #23） | **完整回归** |
| 存储层变更 | Room 表/DAO/Migration、DataStore、归档、游标（如 #30 / #32） | **完整回归** |
| 渲染/UI 结构变更 | ChatMessageList 重组、Markdown 渲染、滚动补偿、List item 结构（如 #16） | **完整回归** |
| 性能优化 | 日志风暴清理、排序移除、反射 hack（如 #39 / #42 / #43） | **完整回归**（必须采集性能基线） |
| 单文件 bug 修复 | 改一个条件、一个索引、一个字符（如 #37 args[8]→args[9]） | **快速回归** |
| 纯 docs/文案/i18n | 注释、文档、字符串翻译 | **免回归**（仅 i18n-check） |

**判断原则**：拿不准时用更高级别。代价是时间，收益是防回归——回归漏检的修复成本远高于多跑一轮验证。

### 1.3 触发时机

- 任何 PR 合入前
- 任何"声称完成"前（对齐 verification-requirements.md 铁律）
- 发版前（叠加 `docs/release-workflow.md`）
- 跨层重构收尾

## 2. 验证维度框架（D0-D4）

> 命令细节、超时、通过标准见 `docs/verification-requirements.md`。本节只规定**何时必须**与**回归专属要点**。

| 维度 | 内容 | 何时必须 | 通过标准 | 引用 |
|------|------|----------|----------|------|
| **D0 编译+静态** | `compileDevDebugKotlin` + 全量单测 + `compileDevDebugAndroidTestKotlin` + `scripts/i18n-check.ps1` | 所有变更 | BUILD SUCCESSFUL / 0 failures / i18n 0 error | verification §维度 1 |
| **D1 单测分层** | 先受影响模块 `--tests`，再全量 `--rerun`（防 UP-TO-DATE 跳过） | 所有变更 | 0 failures | verification §维度 1、§4a |
| **D2 模拟器功能走查** | 按本文档 §3 能力域清单执行相关项 | UI/状态/存储/连接任一变更 | §3 表格"预期结果"全部通过 | verification §维度 2b |
| **D3 性能可观测** | gfxinfo 帧率/janky、logcat 日志量、GC、内存、冷启动 | 性能优化 / 渲染变更 / 完整回归 | **修复前基线对比**：不得退化 | verification §维度 3、§2.1 |
| **D4 用户人工验收** | 时间性现象（动画/闪烁/滚动稳定性/布局跳动） | UI 变更触及时间性现象 | 用户反馈记录 | verification §维度 5 |

### 2.1 D3 性能基线对比原则（回归专属）

性能优化类变更**必须先采集基线**：

1. **改动前**：在干净分支采集指标（gfxinfo p50/p90/p99、janky %、logcat 行数/s、冷启动 ms）
2. **改动后**：同场景、同设备、同数据量复测
3. **对比**：退化 >10% 必须解释或回滚

已有基线证据可引用：`docs/research/audit-2026-08-10/E-emulator-measurements.md`（模拟器渲染基线）、`A-rendering-pipeline.md`（渲染管线债务清单）。

### 2.2 常用采集命令

```bash
# 帧率/Jank（滚动后采集）
adb shell dumpsys gfxinfo <package> > gfxinfo.txt

# 冷启动（am start -W 报告 TotalTime）
adb shell am start -W -n <package>/<MainActivity>

# 日志量（运行 60s 后统计行数）
adb logcat -d | Measure-Object -Line

# 崩溃缓冲区
adb logcat -b crash -d

# dropbox 崩溃/ANR 扫描
adb shell dumpsys dropbox --print
```

## 4. 问题处理流程

```
发现问题（复现 + 收集证据：logcat / 截图 / 操作步骤 / 设备型号）
  │
  ├─ 判断影响面
  │
  ├─【阻塞性】功能不可用 / 数据丢失 / 崩溃 / 严重性能退化 / 主流程阻断
  │     → 必须根因修复
  │     → 修复 → 验证（D0-D2 复跑受影响项）→ 完成
  │
  └─【非阻塞】体验瑕疵 / 边缘场景 / 优化项
        → 登记 backlog.md（引用证据路径）
        → 继续回归
```

### 4.1 修复原则

- **优先根因修复**：解决源头，不留技术债。AGENTS.md「精准修改」要求外科手术级，不顺手改无关代码。
- **根因修复牵扯过大时**：允许临时补丁，但必须三件事齐全：
  1. 代码注释 `TODO`/`FIXME` 标注（当时情况 + 为什么临时 + 根因方向）
  2. `backlog.md` 登记技术债条目（现象 / 临时方案 / 根因分析 / 修复建议 / 当时考虑）
  3. 后续重构者能从注释 + backlog 理解当时决策（反例见 `docs/research/audit-2026-08-10/D-patch-vs-rootcause-history.md`）
- **反射 hack 类补丁**（如 #43 Compose internal 反射）：注释必须写明依赖的 Compose 版本与字段名，升级前手动测试。

### 4.2 禁止行为

- ❌ **静默跳过问题**——每项发现必须有处置记录（修复 / 登记 / 说明为何非 bug）
- ❌ **"自动化都过了所以不算问题"**——D4 时间性现象以用户反馈为准（verification §维度 5）
- ❌ **删除/注释失败测试让其通过**——失败测试必须分析根因（参考 #21 / #22 系统性调试范例）

### 4.3 backlog 登记格式（摘要）

完整格式以 `backlog.md` 自身为准。核心字段：

```
- [<状态>] **#<编号> <标题>** `<tag1>` `<tag2>`
  - 问题：现象描述
  - 修复：方案（或"待复现"）
  - 来源：<证据路径 / 走查编号 RG-XX / 用户反馈>
```

状态流转：`[ ]` 进行中 → `[~]` 待验证 → `[x]` 已完成（用户确认后方可勾选）。

## 5. 证据与报告规范

### 5.1 证据落盘

- 路径：`docs/research/<topic>/metrics/` 或审计目录（如 `docs/research/audit-2026-08-10/`）
- 命名：`RG-<编号>-<描述>.<ext>`（如 `RG-04-draft-restored.png`、`RG-13-crash-buffer.log`）
- 内容：截图（PNG）+ UI dump（XML）+ logcat（LOG）+ gfxinfo（TXT）+ db 快照

### 5.2 回归报告模板

每轮回归输出一份报告（参考 `RG-regression.md` 结构）：

```markdown
# RG — <scope> 回归走查报告（commit <sha>，backlog #<n>）

- 被测版本 / commit / 环境 / 日期 / 方法
## 结论
<通过/失败统计；关键风险>
## 走查结果表
| # | 项目 | 结果 | 关键证据 | 证据文件 |
## 发现的异常/注意事项
<逐项：现象 / 影响 / 定性（回归 or 预有 or 设计）>
## 验证维度小结
<D0-D4 各维结论>
## 证据清单
<RG-* 文件列表>
```

### 5.3 提交

回归证据与报告**随变更 commit**（或同 PR）。发版回归证据归档到对应 release 目录。

## 6. 快速回归 vs 完整回归

| 场景 | D0 | D1 | D2 | D3 | D4 | 能力域 |
|------|----|----|----|----|----|--------|
| **免回归**（纯 docs/i18n） | i18n-check | — | — | — | — | — |
| **快速回归**（单文件小修，如 #37） | ✅ | 受影响模块 `--tests` | 受影响能力域 ★ 必测点 | — | 触及时间性时 | 1-2 域 ★ |
| **完整回归**（接口/状态机/存储/渲染/性能，如 #38 / #30 / #16） | ✅ | 全量 `--rerun` | §3 全清单 | ✅ 基线对比 | ✅ 清单 | 全 12 域 |

### 判断示例（真实案例）

| 案例 | 变更类型 | 级别 | 理由 |
|------|----------|------|------|
| #37 args[8]→args[9] | 单字符 bug 修复 | 快速 | 单行修改，影响面 = 工具进度 UI |
