## 四、#295 残项：缩略图渲染成文件 chip（ea88903f）

### 真机验收发现（部分通过）

- 扫描+拉取链路工作：`attachment scan: msgs=58 candidates=1` → `attachment fetch enqueue` → `session.attachment` 200 → `candidates=0`（patch 落地）→ **1.6s 后又 `candidates=1`**（不再 enqueue）；
- 但截图裁决：附件渲染为「📎 image/png」通用文件 chip 而非图片缩略图；杀进程重进同模式（重新成为候选、重新拉取）。

### 根因（candidates 1→0→1 翻转定音）

`MessageMergeEngine.mergePart` 对 `Part.File` 落入 `else -> incoming`——File 的 `url` 是**客户端补丁字段**（DSH 附件 bytes 经 session.attachment 拉取后由 patchFileUrl 写入，服务器事件/REST 快照恒 url=null）：REST/回放重刷即把已 patch 的 data-url 抹掉 → 缩略图退回文件 chip；且 `attachmentUrlCache` 按_attId_去重挡住重试 → 永久文件 chip。

### 修复（两层）

1. `mergePart` 加 File 分支：`incoming.url == null && existing.url != null → incoming.copy(url = existing.url)`（incoming 保持权威，url 仅客户端侧保留）；
2. ChatViewModel 扫描兜底：候选重现且缓存已有非空 url → 直接 patchFileUrl 直补（免二次网络请求）。

- 测试 +3（mergePart 保留/incoming 权威/mergePartsList 端到端）；全量 2532/0/0。
- 附带说明：杀进程后重新 fetch 一次是 by-design（attachmentUrlCache 进程内存、无持久层，服务器是 bytes 真相源）；「跨进程持久」的验收标准 = 重进后缩略图能重新渲染出来，而非不发起请求。
