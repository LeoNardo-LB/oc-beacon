## 一、#569 发送链超时——根因定案+双层修复（commit 963992b41）

**触发**：用户裁决浸泡遗留项 ①②（"设置一个目标，开始修复1、2吧，并且要求确保质量，要有完整的测试"）。

**根因定案（推翻卡片原假设"HTTP 读超时缺失"）**：
- Ktor 3.5.2 反汇编实证（ktor-client-okhttp/ktor-client-core 本地缓存字节码）：
  - OkHttp engine `setupTimeoutAttributes` 只映射 connect→connectTimeout、socket→read/writeTimeout；**requestTimeoutMillis 不进 engine 配置**；
  - 但 HttpTimeout 插件在 Send 管线自装 request-timeout killer（`getSupportsRequestTimeout`=非 WS/非 SSEClientContent 即生效；到点取消请求执行上下文抛 HttpRequestTimeoutException）——requestTimeout 在本引擎下有效，由插件层实施；
  - SSE 客户端以 `requestTimeoutMillis=Long.MAX_VALUE` 显式豁免（字节码 offset 5-13：==MAX_VALUE 即 return）——长流不限时契约在位。
- 265s+ 拼图闭合：V2 发送链 = switchModel → switchAgent（**runCatching 吞 120s 超时**）→ prompt 三串行调用，各吃 client 级 120s requestTimeout（NetworkModule 自 2026-07 就有，浸泡时在位）——被吞的 120s + 最终调用 120s + 开销 ≈ 265s 后才见失败框（A-10 观测窗口内无超时无反馈）。

**修复（双层）**：
- per-request：`data/api/SendChainTimeout.kt`（30s request + 10s connect + 30s socket）→ V2ApiClient switchModel/switchAgent/prompt、V1ApiClient prompt_async 接线（DSH 走链级死线覆盖）；
- 链级：ChatSendDelegate 网络段 `withTimeout(SEND_CHAIN_DEADLINE_MS=65s)`；TimeoutCancellationException 在通用 CancellationException 再抛**之前**拦截→失败对话框（防静默失败——超时取消形态是 CancellationException 子类，不拦则 spinner 停而无反馈）；
- NetworkModule 注释修正（机制真相），全局 120s 兜底保持不变（不波及 import/pty 等慢 REST 域）。
