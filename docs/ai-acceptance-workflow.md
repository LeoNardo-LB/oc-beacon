# AI 真机验收工作流（AI Acceptance Workflow）

> **定位**：backlog 卡片交付验收的唯一操作协议（2026-09-04 用户裁决，/grill-me 定稿）。
> 目标：最大限度减少人工介入——凡 AI 可通过仪器与真机自动化完成的验收，全部由 AI 完成。
> 配套：[qa-methodology.md](qa-methodology.md) §4.4（关闭门槛）· [verification-requirements.md](verification-requirements.md) V6 · [real-device-testing.md](real-device-testing.md)（真机 runbook）· [regression-guide.md](regression-guide.md)（回归域）

---

## 0. 总则（执行任何卡片前先读）

1. **逐卡串行**：一次只做一张卡；卡内「开发 → 验收 → 回归 → 关闭/挂人工」完成后才进下一张。
2. **真机独占**：真机只有一台，一切真机操作严格串行（§5）；禁止多个 subagent 并发操作真机。
3. **根因修复纪律不变**：禁止补丁式修复；过渡措施必须登记根因卡并标「过渡措施」。
4. **决策方向**（遇到设计分叉时按此裁夺）：整体最优 > 移动端 UIUX 友好 > 复用已有能力/组件 > 根因修复/架构优化/不留技术债。冲突时向前者让步，并在 journal 记录裁决理由。

## 1. 卡片分类与关闭权限（2026-09-04 用户裁决）

| 分类 | 判定 | 关闭条件 |
|---|---|---|
| **非 UIUX** | 无用户可见 UI 变化（数据/wire/逻辑/后台/工具链） | 三步验收全绿 + AI 以可观测性手段（logcat/Room 直查/网络证据/服务器端效果）取得**确凿证据** → **直接关闭**，迁入 journal |
| **UIUX** | 卡内含任何用户可见 UI 变化 | 先完成同左的 AI 三步验收全绿（含 §6 录屏证据），再追加**人工验收清单**；人工确认后才关闭 |

- 分类粒度：UI 部分走人工清单，非 UI 功能部分仍以 AI 证据关闭——混合卡按 UIUX 类处理但不重复验收。
- 人工验收清单按**域边界汇总**一次性提交用户（如：#326+#327 域完→一份清单），不逐卡打断。
- 证据标准（继承 #308 事后定律）：「成功」必须有**受端效果证据**（执行/恢复/UI 状态变化），网关 ok 不算证据。

## 2. 三步验收法（每卡必走，顺序不可颠倒）

### 步骤 1 · 验收文档生成（主 agent）

- 位置：`docs/acceptance/YYYY-MM-DD-<编号>-<slug>.md`，一卡一份，单文件自包含。
- 默认在开发/修复完成后生成（此时分支清单最准确）；大特性可先出草稿、执行前定稿。
- **覆盖三块**：① 新特性功能点 ② bug 修复效果 ③ **受影响关联模块回归**（regression-guide 12 能力域 ∩ 本卡触面，逐域列明为何回归/不回归）。
- **每个 item 必填字段**：
  - `目的`：校验<具体场景/情况>下<具体表现>——一句话精准自然语言，无歧义指代
  - `前置`：设备状态/服务器/会话/数据/构建版本准备
  - `操作`：可被照做的步骤序列（adb 命令、UI 路径、坐标/dump 定位）
  - `期望`：可观测现象
  - `判定`：成功标准，尽量指向仪器证据（logcat tag、DB 行、探针文件、UI dump 节点、服务器端观测）
- **质量标准**（审查依据，也是生产标准）：item 边界清晰、职责单一、**互不重叠不模糊**；覆盖本卡改动**全部分支**（正向+逆向+边界，L1 连接层→L2 数据面→L3 交互面→L4 回归面层层递进）；达到可直接上生产水准。
- 模板见 §8.1。

### 步骤 2 · 验收文档审查（纯净上下文 subagent）

- 委派一个**无主会话上下文**的 subagent，只给：checklist 文件路径 + 本文件 §2 步骤1 质量标准。
- 审查维度：覆盖完整性（分支全覆盖？回归域选对？）、item 正交性（有无重叠/模糊）、可执行性（操作能否照做）、判定可观测性（成功标准可机器/仪器核对？）、前置充分性（会不会跑到一半缺环境）。
- 产出：`PASS` 或逐条修改意见（指到 item 编号）。主 agent 修订 → 复审 → 通过才进步骤 3。
- 模板见 §8.2。

### 步骤 3 · 验收执行（纯净上下文 subagent，持真机锁）

- 委派**新的**干净上下文 subagent，只给：checklist 路径、真机 runbook 路径（real-device-testing.md + android-ui-probing-guide.md）、设备 serial、待测 APK 路径/已装版本。
- **执行纪律**：
  1. **一个 item 一个 item依次执行**，禁止跳项、禁止合并多项一次做。
  2. 每项完成立即在 checklist 对应 item 的`实测记录`区打 ✔ 或 ✘，并**忠实记录一切可观测内容**：logcat 关键行、dump 节点、截图/录屏路径、时间戳、实际现象描述。
  3. **执行期间禁止分析、归因、修复**——只观测与记录；分析由主 agent 在报告返回后进行。
  4. 失败项记录完后**继续**执行后续不依赖它的 item；依赖项标 `BLOCKED-by-<id>` 并记录阻断原因（仍是观测事实，不是分析）。
  5. 全部 item 到达终态（✔/✘/BLOCKED）才结束，产出=逐项打标后的 checklist 文件本身。
- 模板见 §8.3。

### 失败循环（步骤 4）

任何 ✘ → 主 agent 系统性**根因分析**（diagnosing-bugs 纪律：红测试→定位→修复→绿）→ 根因修复 → **只重跑受影响 item**（改动影响面变化则先修订 checklist 并重审）→ 循环直到全绿。循环中新发现问题按 §4 处理。

## 3. 验收前的开发流程（不变式）

每卡仍走既有开发/修复流程：journal 批次记录（backlog-new-batch.sh）→ 红→绿测试 → `compileDevDebugKotlin` → `testDevDebugUnitTest --rerun` → 装真机（real-device-testing runbook）→ 进入 §2 三步验收 → commit（feat:/fix: 前缀强制）。ChatScreen.kt 编辑协议、SSE 滚动铁律、i18n 15 语言等专项纪律在任何卡内继续生效。

## 4. 过程发现的新问题入队策略（2026-09-04 用户裁决）

默认：**登记 backlog + 纳入本批修复队列**。仅当满足任一条件时可只登记不修：

1. 级联发现的**轻微问题累计超过 10 个**（第 11 个起可转只登记）；
2. 问题**改动面/影响面大**（需架构级变更或跨多模块重构）；
3. **硬阻碍**无法解决（外部依赖/厂商限制/需用户凭据）。

只登记不修的，批次末向用户统一报告清单再定。

## 5. 真机串行纪律

- 真机（单一设备）是独占资源：**同一时刻只允许一个验收执行流操作设备**。
- 粒度：一次一卡 → 卡内一次一项；**禁止**多个 subagent 并发操作真机。
- 可与真机执行并行（不碰真机、不碰 Gradle）：checklist 生成/审查、代码分析与编写、单测。
- Gradle 构建同 checkout 禁止并发（AGENTS.md 铁律，与真机锁相互独立）。
- 设备操作一律走 runbook：入口 `./scripts/debug-entry.sh`、pm install 静默装、adb reverse、uiautomator dump/tap。

## 6. 时间性 UI 现象（V6 边界）

- 闪烁/动画/时序/布局跳动类 item：操作步骤中指定 `adb screenrecord` 录制，用 video-analyzer 技能审录像素材作为**客观观测证据**。
- 该类现象属 UIUX → 最终仍以人工验收清单收口（§1）；AI 录屏分析作为前置证据压低人工轮次成本。

## 7. 与既有文档的关系

- qa-methodology §4.4：本文件 §1 细化其关闭门槛（非 UIUX 类 AI 证据确凿即可关闭；UIUX 类追加人工）。
- verification-requirements V6：触发条件不变，执行形态=域边界汇总清单 + 录屏前置证据。
- real-device-testing.md：真机操作 runbook，本文件 §5 引用其入口。
- regression-guide：§2 步骤1 的回归域选择依据。

## 8. 模板

### 8.1 checklist 文件骨架

```markdown
# <编号> <标题> 验收 checklist

- 卡片：backlog #<编号> | 日期：YYYY-MM-DD
- 构建：<commit-hash> <flavor> | 设备：<serial>
- 分类：UIUX / 非 UIUX（决定是否含 §人工清单）
- 回归域：<regression-guide 能力域列表 + 一句话理由>

## A. 新特性 / 修复效果
### A1 <目的一句话>
- 前置：
- 操作：
- 期望：
- 判定：
- 实测记录：（执行 subagent 填写：✔/✘/BLOCKED + 观测事实 + 证据路径）

## B. 回归
### B1 <目的一句话>
- …（同上结构）

## 人工验收清单（仅 UIUX 卡；域边界汇总提交）
- [ ] <操作路径 + 预期现象 + 判定标准>
```

### 8.2 审查 subagent 委派模板

```
你是验收文档审查员。读取 docs/acceptance/<file>.md，按以下标准逐维度评审：
1) 覆盖完整性：改动分支（正向/逆向/边界、L1-L4 层次）是否全覆盖？回归域选择是否合理？
2) item 正交性：有无重叠、职责不清、模糊表述？
3) 可执行性：操作步骤能否照做（命令/路径/定位明确）？
4) 判定可观测性：成功标准是否可仪器核对？
5) 前置充分性。
输出：每维度 PASS/FAIL + 指向 item 编号的具体意见；最终结论 PASS 或 NEEDS-REVISION。
禁止修改文件；只输出评审结论。
```

### 8.3 执行 subagent 委派模板

```
你是真机验收执行员。步骤：
1) 读 docs/acceptance/<file>.md（含每项判定标准）。
2) 读 docs/real-device-testing.md 与 docs/android-ui-probing-guide.md 的相关章节，设备 serial=<serial>，被测构建=<apk 或已装版本>。
3) 按 checklist 顺序一个 item 一个 item执行：准备前置→执行操作→按判定观测→在文件该项「实测记录」区写入 ✔/✘/BLocked + 全部可观测事实（logcat 行、dump 节点、截图路径、时间戳）。
纪律：禁止跳项/合并执行；禁止分析、归因、修复、改产品代码；失败项记录后继续后续独立项，依赖项标 BLOCKED-by-<id>。
4) 所有 item 到终态后：汇总一句每项结果清单返回。
```
