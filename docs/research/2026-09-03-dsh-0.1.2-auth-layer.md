## 1. 结论速览

- **0.1.2 起 `/api` 前缀全量强制鉴权**：RPC POST、双 WS 升级（events.mux/events.host）、`/api/respond`、精确 Fetch 路由——裸调一律 **HTTP 401**（body 恒为 `unauthorized` 六字符）。栅栏顺序固定：**403（Host/Origin fence）→ 401（cookie 鉴权）→ 415（非 JSON POST）→ 200 + result.error 闭集**（旧判别面只在最后一段存活）。
- **鉴权方式唯一：签名 cookie**。一次性**进程启动令牌**只能经 `GET /?token=<43字符>` 交换成 cookie（303 + Set-Cookie → 干净 `/`）；**API 路径与 Authorization header 明确不接受该令牌**（设计笔记「曾考虑的替代方案」专门否决 bearer 路线）。oc-beacon 既有 `auth(conn)` Authorization 通道**对 DSH 无用**。
- **cookie 跨 dsh 重启有效**（HMAC 签名密钥持久化于 `$DSH_HOME/.credentials.yaml`），默认 30 天（`cookieMaxAgeDays` 可配，最小 1）；**绑定 authority（Host 头规范形 hostname:port）**——adb reverse 与 tailscale 直连是两份独立 cookie。
- **双栈可探测**：0.1.1-rc.2 无鉴权、0.1.2 有——客户端发首个 RPC（session.list）按 401/200 分流即可，天然可靠，无需版本预判。
- **我们部署侧 0.0.0.0 patch 存活**：`webserver` 插件 config 级 patch 不经过 CLI flag（0.1.2 CLI 拒绝的是 `--host 0.0.0.0` flag；WebServer 承载层仍收 `'127.0.0.1'|'0.0.0.0'`）。resolveLanTrust 自动信任 LAN/tailscale IPv4 的行为不变。**且 0.1.2 鉴权层恰好堵上 patch 注释里自警的「tailnet 裸奔」缺口**——升级是安全净收益。
- 改造落点（§5）：连接状态机加 `TokenNeeded` 态 + Ktor `HttpCookies` 每服务器持久化 + 401 拦截降级 + token 粘贴 UX；`DshApiClient.kt:563`「DSH 无鉴权」注释与 §2.4 错误层假设同步修订。

## 3. 鉴权层事实卡（全部源码实证）

### 3.1 覆盖面与执行顺序

- 执行点 `packages/client/connection/src/index.ts:117-125`：`/api` **前缀路由**对每个请求先 `requestRejection(req)`——`rpc-host.ts:96-99`：`isTrustedApiRequest(host/origin, trustedHosts)` 不过 → **403 'forbidden'**；过栅栏但 `browserAuth.isAuthenticated` 无有效 cookie → **401 'unauthorized'**；都过才 `bridge` 进 RPC。WS 升级请求同走该前缀路由（传输套件测试固化「WebSocket upgrade 路径上一致的 401/403 行为」）。
- 媒体栅栏：`/api` POST 必须 `Content-Type: application/json` 否则 415（Ktor ContentNegotiation 已满足，无需改）。
- 非 index 静态资产保持公开；index（`/`）走 §3.2 交换端点。

### 3.2 令牌交换（唯一入门口）

`browser-auth.ts` `authorizeIndex`（261-290 行区间）：

- 进门条件**全部**满足才铸 cookie：`GET` + `pathname === '/'` + **恰好一个** `?token=` + timing-safe 匹配进程启动令牌 → `303` + `Set-Cookie` + 重定向干净 `/`。
- 有效 cookie 再访问带（陈旧）token 的 URL → 仍重定向干净 `/`（免换新）。
- 其余一切 index 请求（缺 token/错 token/POST/多数 token）→ 同一份**最小 401**。
- index 交换路径**无 Host fence**（fence 只挂 /api）——token 本身就是秘密；cookie 铸给请求 Host 头的 authority。

### 3.3 令牌与 cookie 形态

| 项 | 值 | 证据 |
|---|---|---|
| 启动令牌 | 每进程随机 32B → base64url **43 字符**；WeakMap 挂根 context（跨 Connection 热重载保留）；**绝不持久化** | browser-auth.ts:53-58,73-79 |
| 打印 | `dsh web: http://127.0.0.1:PORT/?token=… (LAN: http://<lan-ip>:PORT/?token=…)`，**stdout console.log，`--no-open` 只关浏览器不关打印**（URL 行是 supervisor 就绪信号） | bundle/web-app/src/index.ts:271-281 |
| cookie 名 | `dsh-auth-` + base64url(sha256(authority))——每个 authority 确定性命名 | browser-auth.ts:127-129 |
| cookie 值 | `v1.<base64url(payload)>.<base64url(hmac-sha256)>`；payload = `{version:1, authority, issuedAt, expiresAt}` | browser-auth.ts:139-146 |
| cookie 属性 | `Path=/; HttpOnly; SameSite=Strict; Max-Age/Expires`；**无 Secure**（loopback HTTP 前提；tailnet 明文传输需自知） | browser-auth.ts:133-135 |
| authority | `Host` 头经 `new URL('http://'+host).host` 规范化——**hostname:port**；签名进 payload，换地址=换 cookie | browser-auth.ts:100-110 |
| 签名密钥 | `$DSH_HOME/.credentials.yaml` 的 `client-connection/browser-session` grant（版本化 32B）；**跨重启持久 → cookie 30 天内跨 dsh 重启有效**；删记录+重启=全撤销 | browser-auth.ts:169-197 |
| 有效期 | `cookieMaxAgeDays` 默认 30，`z.natural().min(1)` | connection/src/index.ts:80-88 |

### 3.4 配置面（宿主侧可调，无鉴权开关）

`client-connection` 插件 Config：`trustedHosts: string[]`（裸 authority；`0.0.0.0` 绑定下 webRuntime 自动信任非 loopback IPv4 含 tailscale 100.x——resolveLanTrust）· `cookieMaxAgeDays` · `maxRequestBodyBytes`（默认 300MiB）。**没有 auth 开/关**——鉴权不可配置关闭，绕开只能改源码自定义组合（不务实）。

### 3.5 官方交换配方（Node，e2e 实测同款）

```ts
const res = await fetch(launchUrl, { redirect: 'manual' })   // GET /?token=...
const setCookie = res.headers.get('set-cookie')              // 期望 303
const cookie = setCookie.split(';', 1)[0]                    // "dsh-auth-…=v1.…"
// 之后所有 /api 调用: headers { cookie, 'content-type': 'application/json' }
```

## 5. oc-beacon 适配方案（定向，未实现）

### 5.1 连接状态机（新增鉴权维度）

`ServerCapabilities`/`ServerConnection`（serverType=Dsh）增加鉴权态：`Unknown → Probing`（首发 session.list：200=无鉴权[0.1.1] / 401=需鉴权[0.1.2]）`→ Authenticated(cookie) / TokenNeeded`。401 任意时刻可复发（cookie 过期/撤销）→ 降级 TokenNeeded + 排队重试。持久化：cookie 值 + authority + serverVersion 一起进 DataStore（30 天免重输）。

### 5.2 token 获取 UX（Android 现实通道）

- 源头：宿主终端 stdout（`--no-open` 也打印）或 `~/.local/state/dsh-web/web.log` 里 `grep 'dsh web:'`（console 打印落入该 append 日志，实测可回收）。
- 客户端：粘贴整行/整 URL/裸 43 字符 token 三种输入都解析；exchange `GET {base}/?token=`。**exchange 必须用客户端后续实际使用的同一 base**（cookie 绑 authority）：adb reverse 配 `127.0.0.1:3080`，tailscale 直连配 `100.x.y.z:3080`——同一服务器两个地址=各自 exchange（authority 签名互不通用）。
- 可选辅助：宿主侧 `qrencode -t ansiutf8` 出终端二维码扫码录入。
- token 每进程轮换但 **cookie 跨重启有效** → 正常使用下每月至多输一次；dsh 重启不要求重输。

### 5.3 网络层落点（Ktor 3.5.2 + OkHttp 引擎）

- `HttpClient` 装 `HttpCookies` 插件 + **每服务器** CookieStorage（内存 or DataStore 持久化）；OkHttp 引擎下 WS 升级请求自动同源带 cookie。
- `auth(conn)` 扩展点（AuthHeader.kt）DSH 分支**不发 Authorization**，cookie 由插件注入——单一演进点设计直接兑现（#114 注释预言成立）。
- WS：升级 401 → 与 HTTP 同路径降级 TokenNeeded；pingInterval(20-30s) 维持设计稿 §1.6 不变（服务端仍零心跳，实测 190s+）。
- 交换器实现要点：`redirect: manual` 语义（Ktor `followRedirects=false` 局部请求），读 `Set-Cookie` 首段；非 303/无 Set-Cookie = token 陈旧（dsh 已重启过）→ 重新索要 token。

### 5.4 错误层（§2.4 重写）

判别顺序：HTTP 403 → 拓扑配置错（trustedHosts/Host 头），文案明确「非 token 问题」；HTTP 401（body `unauthorized`）→ TokenNeeded；HTTP 415 → 请求构造 bug；HTTP 200 + result.error 闭集 → 原有领域映射不变。
