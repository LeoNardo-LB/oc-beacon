# ServerAdapter：服务器类型插件化架构（含 DSH 0.1.5/V3 适配汇合点）

> 状态：**架构定稿（grilling 收敛）**，未实施。2026-09-10。
> 决策来源：grilling 22 项 + 架构自审修正（见 Implementation Decisions 末段）。
> tracker 形态：backlog P0 卡片 + 本文件（唯一权威）。
> 关联：docs/archive/2026-09-10-dsh-0.1.5-rc1-impact.md（DSH 0.1.5 影响调研与适配层评估）。


## Problem Statement

从用户视角：

- 当后端协议（OpenCode V1/V2、DeepSeek Harness 各线面世代）演进时，应用会出现难以理解的退化——某后端升级后会话历史整页空白、实时流式输出消失、子智能体卡片不再出现；新后端能力上线又很慢。
- 每种服务器的私有能力（某后端独有能力与其界面）没有被挂载的位置，只能靠散落的类型判断实现，导致"支持/不支持"的表现不一致。

从开发者视角（根因）：

- 缺一个"服务器类型"的插件化 seam：没有策略 + 工厂/注册表，路由被逐域手写重复；服务器类型判断散落在数据、服务、界面各层。
- 服务器能力是封闭的固定字段集合 + 集中的类型分支：类型私有能力没有位置，只能退回类型判断。
- 界面直接认识具体服务器类型（组件挂载点写类型判断），新增类型要动通用屏幕。
- 事件词汇没有版本维度：后端数据格式升级会击穿历史重建（未知事件默认被当作"不可忽略"而拒绝整段重建），实时流式通道切换也没有被建模。
- 结果：接入一种新服务器类型或适配一次后端破坏性变更，要在几十个文件跨层改动，且容易遗漏。

## Solution

从用户视角：

- 把"服务器类型"变成一个可插拔的适配单元：每种服务器类型由一个适配器描述——它实现哪些域端口、有哪些独有能力、用哪种连接策略、在哪些界面插槽有内容。
- 通用问题（路由、能力查询、能力驱动的界面门控、事件到界面的映射）由架构层统一解决；每种服务器类型的私有能力由该类型自行实现，包括其专属界面。
- 新增一种服务器类型 = 新增一个适配器及其同目录注册，不修改既有共享代码；后端破坏性变更只改该类型的适配层内部（线面世代 / 事件词汇），上层无感。
- 用户可见结果：后端升级不再让历史 / 流式 / 卡片消失；新能力出现时既有行为稳定；能力按能力位显示或隐藏，而不是按类型判断；不支持的能力读操作返回空、写操作显式失败而不是静默成功。

架构一次到位（目标形态完整），开发按切片分批（见 Further Notes）。

## User Stories

应用用户：
1. 作为应用用户，我希望后端升级后会话历史照常渲染，而不是整页空白。
2. 作为应用用户，我希望实时流式输出在任意后端世代都可用。
3. 作为应用用户，我希望子智能体卡片、压缩卡、命令反馈卡等既有卡片在各后端一致出现。
4. 作为应用用户，我希望某后端独有的能力（如目标、权限档、Agent 预设）只在支持它的后端显示，不支持时入口自然隐藏。
5. 作为应用用户，我希望后端遇到未知事件时不崩溃、不丢整段历史，而是降级且可观测。
6. 作为应用用户，我希望新增或切换服务器类型时既有会话与设置不丢失。
7. 作为应用用户，我希望能力探测失败时界面明确显示"未知"，而不是假装全支持或全不支持。
8. 作为应用用户，我希望服务器选择器里出现哪些类型由应用实际支持的适配器决定，而不是硬编码。
9. 作为应用用户，我希望模型目录、提供商、文件、终端等能力在支持的后端自然出现，不支持的后端入口隐藏。
10. 作为应用用户，我希望某后端挂载插件后其独有能力与界面立即可用，不需应用发版（在能力探测可观测的前提下）。

开发者（接入新服务器类型）：
11. 作为应用开发者，我想新增一种服务器类型时只新增一个适配器单元（含其同目录注册），不修改既有共享代码。
12. 作为应用开发者，我想让新类型复用通用机制（路由、能力查询、事件到界面映射、能力位门控），只需实现差异部分。
13. 作为应用开发者，我想让新类型的版本 / 世代差异只出现在该类型的适配层内部。
14. 作为应用开发者，我想让新类型的私有能力自带界面，并挂在稳定的界面插槽上。
15. 作为应用开发者，我想在编译或测试期就被提示缺失或不一致（注册表覆盖校验、契约测试），而不是运行到一半才发现。
16. 作为应用开发者，我想让"某能力是否存在"只有一个真相来源（端口是否实现），而不是多处手写布尔。
17. 作为应用开发者，我想让不支持某能力的服务器类型对该能力的读返回空、写显式失败。
18. 作为应用开发者，我想让 OpenCode 的 V1/V2 与 DSH 的各线面世代用同一种"类型内子策略"模型，而不是各写各的。
19. 作为应用开发者，我想在 Application 启动期就校验适配器注册完整，缺失即失败暴露。

后端适配维护者：
20. 作为后端适配维护者，我想用"线面世代 + 事件词汇表"按代描述差异，新增一代只加一个世代描述，不改上层。
21. 作为后端适配维护者，我想让未知事件默认降级并计数，只有结构性违约才拒绝重建。
22. 作为后端适配维护者，我想能用真实会话日志黄金样本按代断言映射结果。
23. 作为后端适配维护者，我想让能力探测与版本探测合并为一次握手，避免重复往返。

界面维护者：
24. 作为界面维护者，我想让通用屏幕只渲染"注册到某插槽的扩展"，不认识任何具体服务器类型。
25. 作为界面维护者，我想让私有界面扩展开关由能力位驱动，而不是类型判断。
26. 作为界面维护者，我想让能力位由类型适配器提供，而不是在领域模型里集中分支。
27. 作为界面维护者，我想让界面插槽契约（槽位集合）在架构上先定义，实现可分批。
28. 作为界面维护者，我想让每个私有界面扩展在自己包内注册，不集中维护清单。

架构维护者：
29. 作为架构维护者，我想让路由只有一处 seam，而不是每个域重复一份类型分支。
30. 作为架构维护者，我想让服务器类型判断只允许出现在白名单（类型定义、持久化身份、用户选择、调试），其余归零。
31. 作为架构维护者，我想让连接策略可替换，且连接编排不把平台服务生命周期混进策略。
32. 作为架构维护者，我想让能力缓存按（服务器、世代）失效，重连或世代变化即重算。
33. 作为架构维护者，我想让领域层保持纯净（不依赖界面框架 / 平台），以便将来可抽取。
34. 作为架构维护者，我想让新增类型是"注册即生效"，而不是"改中心清单"。

QA / 验收：
35. 作为验收者，我想用同一套契约测试跑遍所有适配器（含一个假适配器），证明"新类型即插即用、上层无感"。
36. 作为验收者，我想用真实服务器（容器旧版本 + 在役新版本 + 真机）做端到端验收。
37. 作为验收者，我想用机械门禁防止新增服务器类型判断回流。
38. 作为验收者，我想让"服务器类型判断归零到白名单"成为可机械核对的交付条件。

## Implementation Decisions

分层与依赖方向
- 领域层（domain）：纯契约，不依赖界面框架与平台；只放跨层、与界面无关的契约。
- 界面层（ui）：通用屏幕 + 界面扩展注册；依赖领域契约，不依赖具体服务器类型实现。
- 数据层（data）：各服务器类型的适配器实现与协议内部细节（世代画像、事件词汇表）。
- 服务层（service）：连接监督与平台生命周期（前台服务、通知），经领域契约调用数据层。

唯一路由 seam
- 新增领域接口 ServerAdapterResolver（按连接或按类型解析适配器）与数据层实现；删除各领域现有手写类型路由门面，调用方经该 seam 取端口。域端口接口本身保留，作为策略契约。

注册与选择
- 每个适配器在自己包内以集合多绑定贡献一个适配器实例；注册表构造期校验重复键与全类型覆盖；Application 启动期强制解析一次（缺失即崩溃暴露）。
- 服务器类型枚举保留为"产品支持的封闭集合 + 持久化身份"（唯一共享触点）；服务器选择器改为由注册表枚举驱动，注册了适配器即自动出现。

适配器契约（决策密集的类型形状）
~~~kotlin
interface ServerAdapter {
    val type: ServerType
    // 该连接的线面世代纯 id（如 v1/v2/v011/v012/v015），不含协议细节
    fun wireGeneration(conn: ServerConnection): String
    fun ports(conn: ServerConnection): ServerPorts
    // 不可由端口推导的核心行为标志（目标：个位数）
    fun coreFlags(conn: ServerConnection): CoreFlags
    // 类型私有能力（自带命名空间），默认空
    fun privateFeatures(conn: ServerConnection): Set<ServerFeature> = emptySet()
    val connectionStrategy: ConnectionStrategy
    // 声明在哪些界面插槽有内容（不含界面代码）
    val uiSlots: Set<ServerUiSlot> get() = emptySet()
}
~~~

能力模型（唯一真相）
- 唯一真相 = 端口可选性：ServerPorts 中可选端口缺席即该能力不存在。
- 能力集合 = 派生能力（由端口可选性派生） + 私有能力；能力对象由框架计算，适配器不手写。
- 核心行为标志只保留不可推导项（压缩是否异步、导出是否为归档、配置是否可写等），逐条按"能否推导"判定。
~~~kotlin
data class ServerPorts(
    val session: SessionApi, val message: MessageApi, val system: SystemApi,
    val file: FileApi? = null, val provider: ProviderApi? = null,
    val terminal: TerminalApi? = null, val shell: ShellApi? = null,
    val subagents: SubagentRepository? = null, val goals: GoalRepository? = null,
    val feedback: FeedbackRepository? = null,
    val serverSettings: ServerSettingsRepository? = null,
    val queue: ServerQueueRepository? = null,
) { fun derivedFeatures(): Set<ServerFeature> /* 端口存在 => 对应能力 */ }

fun ServerAdapter.capabilities(conn: ServerConnection): ServerCapabilities =
    ServerCapabilities(coreFlags(conn), ports(conn).derivedFeatures() + privateFeatures(conn))
~~~
- ServerFeature 是开放的带命名空间 id（如 core.goals、dsh.providerDirectory）；通用能力有具名常量，私有能力由适配器自带命名空间，新增私有能力不改共享代码。

私有能力端口
- 新增通用命名的领域端口：子智能体、目标、反馈、服务器设置（由现有 DSH 专用设置仓库更名而来）、服务器队列。
- 非支持类型语义：端口缺席；读操作返回空，写操作抛"能力不可用"。

版本 / 世代策略
- 线面世代是跨层契约里的纯 id；世代画像（端点到载荷规格）与事件词汇表是适配器内部细节，按代各一个实现，由世代 id 选择。
- 事件映射重构为"共享处理器 + 按代词汇表"；未知事件默认降级 + 遥测，仅结构性违约（事件乱序、种子缺失、表面操作越界）拒绝重建。
- DSH 0.1.5 / 会话格式 V3 适配落点：新增代词汇补全（系统消息、失败尝试、PTC 派发、反馈消息、子智能体目录、产物交付），表面替换指令双读，实时流式走新的按代开关帧。

连接策略
- ConnectionStrategy 采用粗粒度契约：一次握手返回线面世代 + 鉴权态 + 探测状态；运行期负责传输、认证、重连、保活、事件源；不触碰平台服务生命周期。
- 连接监督层退化为薄层：解析适配器连接策略 -> 握手 -> 运行；前台服务、通知、生命周期由监督层从回调驱动。
- 共享实现：SSE 连接策略（OpenCode V1/V2）与多路复用连接策略（DSH）。

界面扩展
- 槽位是领域层纯枚举键（服务器设置、提供商、聊天输入附属、聊天工具栏、会话列表头部），不含界面框架类型。
- 界面层的扩展接口（含界面方法）与注册表由界面层持有；每个私有界面扩展在自己包内以集合多绑定贡献；通用屏幕经组合局部取注册表渲染，不 import 任何具体服务器类型组件。
- 纯数据形态的能力走数据驱动通用组件，不强行进插槽。

不留双轨
- 删除各领域手写路由门面、删除集中式能力分支与连接层的类型分支；不保留旧路径。
- 服务器类型判断白名单（合法保留）：类型定义、持久化身份、用户选择、调试入口；其余全部消除。

决策记录
- 本轮设计经 grilling 22 项收敛，并经一次架构自审修正若干项（契约按层分而非全放领域层；能力改为派生而非保留固定字段集合；能力唯一真相为端口可选性；版本与能力探测合并为一次握手；连接策略不混平台生命周期；服务器类型枚举保留为唯一共享触点）。本文件的 Implementation Decisions 即最终决策集。

## Testing Decisions

什么算好测试
- 只断言外部行为，不碰实现细节。对适配器只断言契约；对上层只断言"不依赖具体服务器类型"。

测试 seam（新增仅 1 个，其余复用既有）
1. 新增：适配器契约 seam —— 一套契约测试跑遍每个已注册适配器 + 一个假适配器。断言：注册表覆盖全部服务器类型且无重复；能力严格等于"端口可选性派生 + 私有能力"；插槽声明与界面注册表贡献一致；不支持端口的读空/写抛；握手契约（世代、鉴权、降级可观测）。该 seam 成立即证明上层无需类型知识。
2. 复用：域端口 seam —— 既有领域端口与仓库接口；本次改路由不改行为，既有单测作为等价网。
3. 复用：事件分发 seam —— 事件层本就服务器无关；按代事件词汇表用真实会话日志黄金样本断言。
4. 复用：真实服务器 seam —— 旧版本容器回归 + 在役新版本宿主 + 真机端到端（验收）。
5. 复用：界面插槽 seam —— 断言注册的界面扩展在其槽位渲染、通用屏幕零类型知识（沿用既有界面 dump 验收手法）。

被测模块
- 适配器注册表与解析器；适配器契约；能力派生；私有端口的不支持语义；按代事件词汇映射；连接策略握手与重连；界面插槽渲染。

既有先例
- DSH 相关单元测试与黄金样本夹具；事件分发器测试；能力位矩阵测试；旧版本容器回归与真机端到端验收脚本。

## Out of Scope

- 不新增第三种真实服务器类型（假适配器仅测试用）。
- 不改变现有用户可见行为（DSH 0.1.5 / V3 适配本身除外）。
- 不新建 PR CI 工作流；机械门禁在发版时生效。
- 不把单模块拆成多 Gradle 模块（依赖方向仍靠约定与门禁）。
- 不清理既有的界面层对数据层的历史直连（与本次架构无关，另立）。
- 不排期 V3 生产修复的具体时间（见 Further Notes 的 hotfix 选项）。

## Further Notes

开发切片（架构一次到位，开发分批；契约在前两片冻结，之后只实现不改契约）
1. 领域契约 + 注册表 + 多绑定；现有两类适配器骨架；既有路由先改走注册表（行为零变化）。
2. 端口可选性派生 + 核心行为标志；删除集中式能力分支与连接对象上的能力 getter；消费点改查能力。
3. 五个私有能力端口化；删除仓库与界面委托里的类型判断守卫。
4. 删除各领域手写路由门面，调用方经解析器取端口。
5. 界面插槽注册表 + 宿主契约 + 私有界面扩展迁移；组合局部提供注册表。
6. 连接策略抽取（SSE 与多路复用两个实现）；连接监督层变薄；一次握手。
7. 按代事件词汇表 + 事件映射重构；完成 DSH 0.1.5 / V3 适配（新架构的首个真实落地汇合点）。
8. 收尾：机械门禁脚本接入发版流程；移除版本探测器里的类型分支；服务器选择器改注册表驱动；假适配器契约测试；架构文档登记该适配层。

代码状态与复查
