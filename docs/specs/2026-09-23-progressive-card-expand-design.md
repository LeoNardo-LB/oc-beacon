# 大卡渐进展开设计调研（#429 spec · 2026-09-23）

> 用户主诉：展开时「等待计算高度」（有时卡 3~5 秒）→ 高度瞬间展开 → 渲染以白屏形式揭示，不美观。期望：展开动画（收起的镜像），边展开边计算高度、从上到下顺序计算，点击即动。
> 本文档为**可行性调研**（用户裁决：先调研不动手），全部结论有仪器级证据支撑。

## 1. 实测时间线（真机 houji，大卡 j7eSbe8T，内容 60 行×4 列表格 H=20352px）

### 1.1 三种场景

| 场景 | 点击→内容可见 | 分解 |
|---|---|---|
| 预热完成（空闲≥1.2s 后点击） | **265ms** | 重组 35ms + settle 89ms + Phase A 22ms + Phase B 幕布 215ms |
| 暖进程但预热未跑（连续操作中点击） | **~2.4s** | ①整列表重组风暴 0.3~1s（含 GC 122MB/190ms）②巨表单片组合+测量 ~1.05s ③A/B 相 360ms |
| 真冷（首次/无预热+账本冷） | **~3~5s** | 上述 ② 变为：表格文本异步解析 0.5~2s（期间 Loading 空白）+ **单帧 2501ms 表格排版测量** + settle |

### 1.2 关键定罪证据

- **MIUIScout 长帧报告**（21:36:35.675，预热路径；21:13/21:16 两笔同签名 2502ms）：`duration=2501ms`，栈= `SimpleMarkdownTable`(MarkdownTable.kt:284 final-pass1 行高测量) ← `SelectableTextAnnotatedStringNode`（可选中文本）← `CardExpandGeometryNode.measure`。**60行×4列=240 个可选中文本单元 × 多遍测量挤在一帧**。
- **toggle 重组风暴**：`toolExpandedStates: StateFlow<Map>`（ChatViewModel:651）每次切换发新 Map → ChatScreen:624 compositionLocal 新值 → 所有消息卡（LocalToolExpandedStates 读者）全量重组（ItemDiag/InjCard 日志洪泛 + GC 122MB）。
- **切片粒度限制**：`sliceStepGroupBodies` 按 PartGroup 边界切片（StepGroupSlicing.kt:40）→ 60 行表格=单 part=**单片 20292px**（SliceHost `win=0..1 total=20292`），窗口化被击穿，视口±1屏≈全表。
- **白屏机制**：Phase A 布局原子开（28.787）与 Phase B drawF 起步（28.790 drawF=0.000→0.004→…）之间，布局已开但内容 alpha≈0/裁剪≈0 → **卡区 3~7 帧纯白**，随后内容自上而下洗入（200ms）。冷场景叠加：解析未完成时揭示区 Loading 空白后内容弹入。
- 预热门 Phase B 揭示本身干净平滑（drawF 0→1 共 215ms，逐帧均匀）；录屏两次均因 8s/30s 窗口恰好截在 Phase B 前而未取到视频帧（日志时间线完整，视觉结论由 DRAW 逐帧参数+白屏机制推定）。

## 2. 架构现状要点

- 引擎（CardExpandReveal 批次十四）：展开=「ε 预热组合 → settle 等内容测高稳定（≤600ms 上限）→ Phase A 布局终态原子落位（withMutableSnapshot driveTo(1f)+配对位移）→ Phase B 纯 draw 幕布揭示」。收起=镜像（幕布收拢→单步原子闭合）。
- 等待的语义：Phase A 需要最终 H 做配对位移；settle 只认「内容驱动重测静止」。**等待不是引擎低效，是「首测即需全高」的构造性代价**。
- 已有资产：StepGroupWindowedBody（视口±1屏组合+账本占位）、片高账本（rememberSaveable 跨收起存活）、finalH 缓存（二次展开即时）、空闲预热（PREWARM_IDLE_MS=1200）。
- 历史教训（约束）：逐帧布局参与族已退役（#420→批次十四：每帧全量重测 ~490ms×N + 锚点重推导泄露帧 ±72/−36）；渲染后补偿族两次被用户否决；ANR 红线（组合期 runBlocking）。

## 3. 用户三问的可行性判决

### 3.1 「点击展开不需要等待计算高度」——**可行，但须拆解 2.5s 单帧巨石**

等待的三成分：(a) toggle 风暴 ~0.3-1s；(b) 表格文本解析 0.5~2s；(c) 表格排版测量 2.5s 单帧。(a)(b) 可独立消除/压缩；(c) 是硬核——**任何调度技巧都救不了一帧内的 240 个文本排版**，必须把测量拆小（表格行组切片）或让首屏所需子集先行。

### 3.2 「边展开边算高度」——**架构上可行，且与退役的逐帧族不同构**

退役的逐帧族问题=每帧**全量**重测+布局动画交叉。而「首窗（视口内）先行终测 + 窗下追加式增长」：增长只发生在折叠线以下（展开期间视口被卡体填满，下方增长**天然不可见**），锚点条目稳定（卡体自身），无需逐帧全量重测。这不是渲染后补偿——对可见区域仍是渲染前计算。

### 3.3 「从上到下顺序计算」——**与既有窗口化方向完全一致**

LazyList/窗口化天然自上而下；缺的只是表格行级粒度。代码中已有明确伏笔（StepGroupBody 分支注释：「单个巨型 text part(如 60 行表格)仍会整条测量……待 AST 级切片」）。

## 4. 方案分层（L0→L3，可叠加）

| 层 | 内容 | 预期效果 | 风险/成本 |
|---|---|---|---|
| **L0 快赢** | ①toggle 风暴收敛：toolExpandedStates 下沉为 per-key 读取（CompositionLocal 拆分或 derivedStateOf per card）②表格单元格测量退出 Selection（SelectionContainer 拆到文本块级，表格用非选中 TextMeasurer）③>2048 文本解析终态缓存（已实现待装，#428 同族） | 2.4s→约 1.2~1.5s；冷场景白屏期缩短 | 低；②需验证长按选择功能取舍 |
| **L1 表格行组切片** | SimpleMarkdownTable 行组化（如 8 行/片）或 AST 行级切片入 StepGroupSlicing；首窗=视口+缓冲只组首片组 | 2.5s 单帧→~6×400ms 分片；settle 只等首窗（~300ms）；点击→动画 ≤600ms | 中；表格 SubcomposeLayout 多遍测量的片间列宽一致性要对齐 |
| **L2 首窗即时展开** | Phase A 以「首窗实测+其余账本/估算」落位；幕布立即揭示首屏 | 点击→可见动画 ~300ms 内 | 中；估算 H 与最终 H 的下方内容位移差（不可见域吸收+集末校准） |
| **L3 完全体渐进** | 首窗 Phase A 即时，窗下每帧一片边动画边组合，账本累积；动画时长自适应组合进度 | 用户设想原样：零等待+全程动画+从上到下 | 高；帧预算耦合幕布节奏（单片仍 80~160ms>帧预算，动画期掉帧需标定）；引擎部分 H 配对位移改造 |

**建议路线**：L0 → L1 → L2 观感验收后再定 L3 是否值得。L0+L1+L2 叠加后体感预期=「点击后 ≤0.5s 内开始平滑展开，首屏内容就位，深处内容滚动前就绪」——已覆盖用户主诉的绝大部分；L3 的边际收益是深处内容也在动画期内就绪，代价是引擎复杂度与掉帧风险。

## 5. 明确不做

- 回归逐帧全量布局动画族（历史定罪，见 §2）。
- 渲染后补偿/拒绘 hold 族（用户两次否决）。
- 组合期阻塞等待（ANR 红线）。
